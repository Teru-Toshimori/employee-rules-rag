## 2. システム概要

### 2.1 目的

社員規則PDFをRAG（Retrieval-Augmented Generation）で検索し、
社員からの質問に対して社員規則の内容を基に回答するシステムを構築する。

利用者はLark上でBotへ質問を送信することで、
社員規則を直接検索することなく回答を取得できる。

### 2.2 システムの特徴

- Larkをユーザーインターフェースとして使用
- Google Cloud Run上でバックエンドを実行
- OpenAI Embedding APIによる文章のベクトル化
- FAISSによる類似文章検索
- OpenAI APIによる回答生成
- 社員規則に記載されていない内容については回答を生成しない
- Cloud Runの最小インスタンス数を0として運用可能
- Larkイベントの重複受信による重複回答を抑止

## 3. システム構成

### 3.1 全体構成

```text
利用者
  │
  │ 質問
  ▼
Lark
  │
  │ HTTP Event
  ▼
Google Cloud Run
  │
  ├─ Larkイベント受信
  │
  ├─ 重複メッセージ判定
  │
  └─ RagService
        │
        ├─ OpenAI Embedding API
        │       │
        │       ▼
        │   質問ベクトル
        │
        ├─ FAISS
        │   └─ 類似チャンク Top 3検索
        │
        └─ OpenAI API
            └─ 回答生成
  │
  ▼
Lark API
  │
  ▼
利用者へ回答
```

### 3.2 RAGデータ作成

```text
社員規則PDF
  │
  ▼
PyMuPDF
  │
  ▼
テキスト抽出
  │
  ▼
条文単位でチャンク分割
  │
  ▼
OpenAI Embedding API
  │
  ▼
文章ベクトル生成
  │
  ├─ openai_index.faiss
  │
  └─ openai_chunks.json
```

RAGデータの作成はCloud Run上では行わず、
開発環境で事前に実施する。

作成したFAISSインデックスおよびチャンクデータを
Dockerイメージへ含めてCloud Runへデプロイする。

            ▼

            │

### 7.2 対象イベント

Larkの以下のイベントを使用する。

```text
im.message.receive_v1
```

テキストメッセージをRAGへの質問として処理する。

## 8. RAG処理設計

### 8.1 質問Embedding

Larkから受信した質問をOpenAI Embedding APIへ送信し、
質問ベクトルを生成する。

使用モデル：

```text
text-embedding-3-small
```

### 8.2 ベクトル検索

生成した質問ベクトルをFAISSで検索する。

検索件数：

```text
Top 3
```

検索された3件のチャンクを回答生成用コンテキストとして使用する。

### 8.3 回答生成

質問と検索されたチャンクをOpenAI APIへ送信し、
社員規則に基づいた回答を生成する。

使用モデル：

```text
gpt-5-mini
```

社員規則から回答を確認できない場合は、以下を返す。

```text
社員規則からは確認できません
```

これにより、社員規則に存在しない内容を推測して回答することを抑制する。

## 12. セキュリティ設計

### 12.1 APIキー

以下の秘密情報はソースコードへ直接記載しない。

```text
OPENAI_API_KEY

LARK_VERIFICATION_TOKEN
```

環境変数から取得する。

### 12.2 GitHub

GitHub上の `.env` は値を空欄にして管理する。

社員規則PDFなどの社内文書はGitHubへ登録しない。

### 12.3 Larkイベント検証

Larkから受信したイベントについて、
Verification Tokenを使用して検証する。

### 12.4 OpenAIへ送信するデータ

質問回答時には社員規則PDF全体をOpenAIへ送信しない。

FAISS検索によって取得された関連チャンクTop 3と
利用者の質問を回答生成用データとして送信する。

## 13. 重複イベント対策

Larkから同一イベントが再送される場合に備え、
`message_id` を使用して重複判定を行う。

処理済みIDはCloud Runインスタンスのメモリ上で保持する。

保持時間：

```text
30分
```

同一IDを再度受信した場合は、
RAG処理およびLarkへの回答送信を実行しない。

### 制約

現在の重複管理はインメモリ方式のため、
以下の場合には処理済みIDが失われる。

- Cloud Runインスタンス再起動
- 別インスタンスでイベントを受信

将来的に必要となった場合は、
永続ストレージを利用した重複管理を検討する。

## 14. ログ設計

ログには秘密情報および質問・回答本文を原則として出力しない。

メッセージ処理確認用として、
message_idの一部のみをログへ出力する。

主なログ：

```text
イベント受信
message_id登録
重複イベント検出
RAG処理完了
Lark回答送信完了
エラー情報
```

Cloud RunのログはGoogle Cloud Loggingから確認する。

## 15. エラー処理

主なエラー対象：

- Larkイベント検証エラー
- OpenAI APIエラー
- FAISS検索エラー
- Lark回答送信エラー

- PDF読み込みエラー

異常発生時はエラー内容をログへ記録し、
秘密情報や質問本文などを不要にログへ出力しない。

## 16. 現在確認されている制約

### 16.1 PDF内画像

現在のPDFテキスト抽出はPyMuPDFによるテキストレイヤーを対象としている。

そのため、画像としてPDF内に配置されている表や文章は
RAGデータへ取り込まれない。

現在使用している社員規則では、
第44条「年次有給休暇」の付与日数表が画像として格納されていることを確認している。

今後、画像内の表をRAGへ取り込む方法を検討する。

### 16.2 Cloud Runコールドスタート

最小インスタンス数を0としているため、
Cloud Run停止状態から最初のリクエストを受信した場合、
起動時間が発生する。

### 16.3 重複管理

現在はCloud Runインスタンス内のメモリで管理しているため、
複数インスタンス間では処理済みmessage_idを共有しない。
