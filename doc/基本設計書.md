## 2. システム概要

### 2.1 目的

社員規則PDFをRAG（Retrieval-Augmented Generation）で検索し、
社員からの質問に対して社員規則の内容を基に回答するシステムを構築する。

利用者はLark上でBotへ質問を送信することで、
社員規則を直接検索することなく回答を取得できる。

### 2.2 システムの特徴

- Larkをユーザーインターフェースとして使用
- Google Cloud Run上でバックエンドを実行
- OpenAI Embedding APIによる文章のベクトル化
- FAISSによる類似文章検索
- OpenAI APIによる回答生成
- 社員規則に記載されていない内容については回答を生成しない
- Cloud Runの最小インスタンス数を0として運用可能
- Larkイベントの重複受信による重複回答を抑止
- PaddleOCRによるPDF内の画像形式の表データ抽出
- OCR抽出結果のテキスト変換
- 条文番号およびページ情報に基づくOCR表データのChunk統合
- OCR抽出データを含むRAG検索用インデックスの生成

RAGデータの作成はCloud Run上では行わず、

OCR処理はRAGデータ作成時に開発環境で実施し、Cloud Run上での質問回答処理時には実行しない。

## 8. RAG処理設計

### 8.1 質問Embedding

Larkから受信した質問をOpenAI Embedding APIへ送信し、
質問ベクトルを生成する。

使用モデル：

```text
text-embedding-3-small
```

### 8.2 ベクトル検索

生成した質問ベクトルをFAISSで検索する。

検索件数：

```text
Top 3
```

検索された3件のチャンクを回答生成用コンテキストとして使用する。

### 8.3 回答生成

質問と検索されたチャンクをOpenAI APIへ送信し、
社員規則に基づいた回答を生成する。

使用モデル：

```text
gpt-5-mini
```

社員規則から回答を確認できない場合は、以下を返す。

```text
社員規則からは確認できません
```

これにより、社員規則に存在しない内容を推測して回答することを抑制する。

### 9.4 PDF画像表OCR処理

#### 9.4.1 機能概要

PDF文書内に画像形式で格納された表データをOCRで抽出し、RAG検索用のChunkへ統合する。

本機能により、従来のPyMuPDFによるテキスト抽出では取得できなかった画像形式の表データを、RAGの検索対象として利用可能にする。

#### 9.4.2 処理対象

- PDF文書内に画像データが含まれるページ
- OCRによって表データとして認識できる画像
- 社員就業規則などの条文形式PDF

なお、条文形式以外のPDFについてもOCR抽出処理を実行可能とする。ただし、条文Chunkへの統合は文書構造に依存する。

#### 9.4.3 処理フロー

1. PyMuPDFを使用してPDFを読み込む。
2. 各ページにOCR対象となる画像が含まれているか判定する。
3. 対象ページを画像化する。
4. PaddleOCR（PP-StructureV3）によって表データを検出する。
5. OCR抽出結果から表のテキストおよび位置情報を取得する。
6. 抽出した表データをテキスト形式に変換する。
7. 表の位置情報および条文情報から対応する条文番号を判定する。
8. 対応するChunkを条文番号とページ範囲に基づいて検索する。
9. 対応するChunkが一意に特定できた場合、OCR抽出データを追加する。
10. 統合後のChunkをEmbeddingおよびFAISSインデックス生成処理へ引き渡す。

#### 9.4.4 対象モジュール

`services/pdf_table_ocr.py`

| 関数名 | 処理内容 |
|---|---|
| `has_significant_image()` | OCR対象となる画像の有無を判定する |
| `extract_pdf_tables()` | PDF内の画像形式の表データを抽出する |
| `extract_table_blocks()` | OCR結果から表データを取得する |
| `html_table_to_text()` | 表データをテキスト形式へ変換する |
| `find_article_for_table()` | 表の位置情報から条文番号を判定する |
| `merge_ocr_tables_into_chunks()` | OCR表データを対応するChunkへ統合する |
| `normalize_ocr_table_text()` | OCR抽出テキストを正規化する |

#### 9.4.5 Chunk統合条件

OCR抽出データは以下の条件を満たす場合に統合する。

- OCR結果から対応する条文番号を取得できること
- 条文番号に一致するChunkが存在すること
- OCR対象ページがChunkのページ範囲内であること
- 対応するChunkが一意に特定できること

条件を満たさない表データは統合対象外として管理する。

また、同一の表データが既にChunk内に存在する場合は、重複追加を行わない。

#### 9.4.6 制約事項

- OCR抽出結果には文字の誤認識が発生する場合がある。
- 表の構造や画像品質によって認識精度が変化する。
- 条文番号を特定できない場合、条文Chunkへの統合ができない。
- 複雑な表レイアウトについては追加検証が必要となる。
- OCR処理は通常のテキスト抽出より処理時間が長くなる場合がある。

## 13. 重複イベント対策

Larkから同一イベントが再送される場合に備え、
`message_id` を使用して重複判定を行う。

処理済みIDはCloud Runインスタンスのメモリ上で保持する。

保持時間：

```text
30分
```

同一IDを再度受信した場合は、
RAG処理およびLarkへの回答送信を実行しない。

### 制約

現在の重複管理はインメモリ方式のため、
以下の場合には処理済みIDが失われる。

- Cloud Runインスタンス再起動
- 別インスタンスでイベントを受信

将来的に必要となった場合は、
永続ストレージを利用した重複管理を検討する。

## 14. ログ設計

ログには秘密情報および質問・回答本文を原則として出力しない。

メッセージ処理確認用として、
message_idの一部のみをログへ出力する。

主なログ：

```text
イベント受信
message_id登録
重複イベント検出
RAG処理完了
Lark回答送信完了
エラー情報
```

Cloud RunのログはGoogle Cloud Loggingから確認する。

## 15. エラー処理

主なエラー対象：

- Larkイベント検証エラー
- OpenAI APIエラー
- FAISS検索エラー
- Lark回答送信エラー
- 不正なイベントデータ
- PDF読み込みエラー
- OCRエンジンの初期化エラー
- PDF画像化処理エラー
- OCR表データ抽出エラー
- OCR対象画像の認識失敗
- OCR表データと条文Chunkの対応付け失敗

OCR抽出データに対応するChunkを一意に特定できない場合は、当該データを統合対象外として管理する。

また、OCR処理中に異常が発生した場合は、原因を確認できるようにログを出力する。
異常発生時はエラー内容をログへ記録し、
秘密情報や質問本文などを不要にログへ出力しない。

## 16. 現在確認されている制約

### 16.1 PDF内画像

### 16.1 PDF内画像およびOCR認識精度

従来のPDFテキスト抽出処理では、画像形式で格納された表データを取得できなかった。

本課題に対してPaddleOCRによる画像形式の表データ抽出機能を追加し、社員就業規則の第44条「年次有給休暇」の表データを抽出して、対応するChunkへ統合できることを確認した。

また、条文形式以外の業務マニュアルPDFについても、画像形式の表データを抽出できることを確認した。

ただし、OCR抽出結果には一部文字認識の差異が確認されており、原本PDFとの完全一致や複雑な表構造への対応については引き続き検証が必要である。

### 16.2 Cloud Runコールドスタート

最小インスタンス数を0としているため、
Cloud Run停止状態から最初のリクエストを受信した場合、
起動時間が発生する。

### 16.3 重複管理

現在はCloud Runインスタンス内のメモリで管理しているため、
複数インスタンス間では処理済みmessage_idを共有しない。
